# Fuseki（布局）— 这手棋值不值得下

Side project 编码前的价值判断。回答的唯一问题是「该不该做」，不回答「怎么做」。

先手原则：编码是后手，判断是先手。在这里被 Kill 的想法，是省下的最贵的时间。

## 判断之前，先看盘面

按顺序收集，缺哪项补哪项，不凭记忆脑补：

1. **现状快照**：如果想法基于已有项目，读代码确认它现在真实的样子（能做什么、谁在用、依赖什么）。
2. **对标**：找 2-3 个直接竞品或成熟同类产品（用 web search 查活的，不背旧知识）。它们怎么做这件事？做到什么程度？定价多少？如果一个对标都找不到，这本身是重要信号——要么是空白机会，要么是别人验证过不值得，必须判断是哪种。
3. **可借鉴的开源实现**：搜有没有开源项目已经解决了核心难题。有，则列出仓库和可抽取的机制；这直接改变「做」的成本估计。
4. **使用者约束**：从长期记忆和知识库等实时来源（agent memory、个人知识库的语义检索）拉取使用者当下的真实约束——可投入时间、维护人力、分发渠道、商业模式、明确说过的偏好。检索不到就直接问，不要脑补。判断必须基于这些真实约束，不是通用权衡。

## 商业就绪四问

想法涉及收费或获客时必答，纯自用工具跳过：

- **谁付钱**：具体的用户画像和付费意愿证据（对标产品有人付费 ≈ 证据；「我觉得有用」≠ 证据）。
- **怎么被找到**：SEO 词、社群、还是平台分发？没有分发答案的产品默认 Kill。
- **凭什么选你**：对标之下的楔子（wedge）是什么？「更便宜」和「用 AI 做的」都不是楔子。
- **维护成本**：上线后每月要花多少小时养它？API 涨价 / 平台改规则时死不死？

## 输出格式（固定）

第一行：**Kill** / **Keep** / **Pivot** 三选一。无前言。

然后：

- **三条理由**，基于上面收集的事实和使用者的真实约束，禁止通用权衡。
- **对标清单**：产品名 + 一句话（它做到哪、你的差异在哪）。
- **可借鉴**：开源仓库或参考实现，各配一句「抽什么机制」。没有则写「无，需全自研」并说明这对成本的影响。
- **Entity delta: +N / -N**——新增的长期维护实体（服务、依赖、账号、定时任务）。+0 是最好的答案。
- 若 **Pivot**：每行一个具体方向，可直接拿去再跑一轮 fuseki。
- 若 **Keep**：最脆弱的假设一句话（「此判断假设 X，X 不成立则 Y」）。

## 边界

- 不出实现方案，不写代码，不画架构。Keep 之后的「怎么做」交给 plan mode。
- 只给一个 verdict，不列选项、不两面下注。
- 用户对 verdict 有异议时，问异议针对哪条事实或哪条理由，只重查那一条，不整体重跑。
